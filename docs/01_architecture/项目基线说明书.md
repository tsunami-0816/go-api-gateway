## 1. 项目核心目标

### 1.1 核心问题

在微服务架构下，外部流量缺乏统一入口，导致以下问题必须被解决：

1. **路由分散**：各服务独立暴露端口，客户端需感知服务地址，无法统一管理路径映射与转发规则。
2. **流量失控**：缺少接口级限流与熔断机制，突发流量可直接击穿下游服务，引发级联故障。
3. **发布风险高**：服务版本升级只能全量切换，无法按比例灰度验证，回滚成本高。
4. **故障定位慢**：请求跨网关、服务、数据库多层传递，无统一 TraceId，问题排查依赖人工串联日志。
5. **本地开发重**：传统网关方案依赖多节点 etcd 集群、完整可观测栈等重型组件，16GB 内存个人开发机无法完整运行验证场景。

### 1.2 业务价值

| 价值维度 | 具体表述 | 可验证标志 |
|---|---|---|
| 统一入口 | 所有外部请求经网关单一入口转发，客户端无需感知后端服务实例地址 | 网关以外无服务端口直接对外暴露 |
| 流量防护 | 限流+熔断在网关进程内原生生效，峰值流量不穿透至下游 | 压测注入 2 倍峰值流量时，下游服务请求量不超过限流阈值 |
| 平滑发布 | 新版本可按指定比例接收流量，异常时秒级回滚 | 灰度比例从 0%→100% 逐级调整过程中，服务零重启、连接不中断 |
| 快速排障 | 全链路 TraceId 透传，单次请求可串联网关→服务→数据库全部调用 | 任意一条请求日志可通过 TraceId 检索到完整调用链，覆盖率 100% |
| 轻量开发 | 全套核心功能在 16GB 开发机上可完整运行与验证 | `docker compose up` 一键启动后，IDE+浏览器+网关全套环境剩余可用内存 ≥4GB |

## 2. 核心指标量化

以下所有指标均来自原始描述，已将定性表述转化为可测量、可验证的数值。每项指标标注测量方法与达标阈值。

### 2.1 性能指标

| 编号 | 指标名称 | 达标阈值 | 测量方法 | 测量环境 |
|---|---|---|---|---|
| P-01 | 单实例 QPS | ≥ 10,000 | 使用 wrk / hey 压测工具，持续 60s，取稳定段平均值 | i5-12500H + 16GB，单实例网关转发至本地测试服务 |
| P-02 | 平均延迟 | < 2 ms | 同上压测，取端到端平均响应时间（含网关转发，不含下游业务处理） | 同 P-01 |
| P-03 | 错误率 | < 0.01% | 压测期间 5xx 响应数 / 总请求数 × 100% | 同 P-01 |
| P-04 | 网关进程内存占用（运行时） | < 100 MB（目标 ≤ 80 MB） | `ps` / 任务管理器读取网关进程 RSS，压测稳定 5 分钟后取值 | 同 P-01 |
| P-05 | 网关进程内存占用（压测峰值） | ≤ 80 MB | 压测峰值期间连续采样 10 次取最大值 | 同 P-01 |

### 2.2 流量治理指标

| 编号 | 指标名称 | 达标阈值 | 测量方法 |
|---|---|---|---|
| G-01 | 限流算法支持 | 同时支持令牌桶与漏桶两种算法 | 代码审查 + 配置切换验证，两种算法均可独立生效 |
| G-02 | 限流粒度 | 接口级（按路由路径 + HTTP Method 维度） | 对 /api/a 配置 100 QPS 限流、/api/b 不限流，验证 /api/a 被限流而 /api/b 不受影响 |
| G-03 | 熔断触发条件 | 支持基于错误率 / 慢调用比例触发 | 注入 50% 错误率，验证熔断器在设定窗口内打开 |
| G-04 | 熔断恢复 | 半开状态探测成功后自动关闭 | 熔断器打开后，下游恢复正常，验证在设定超时后自动放行探测请求并恢复 |
| G-05 | 灰度发布粒度 | 按流量比例（0%–100% 可配置） | 配置 20% 灰度，发送 1000 笔请求，验证新版本接收比例在 18%–22% 区间 |
| G-06 | 流量染色 | 支持基于请求头 / 用户标识染色 | 携带指定 Header 的请求 100% 路由至灰度版本 |
| G-07 | 核心服务可用性（峰值期间） | ≥ 99.99% | 注入 2 倍设计峰值流量持续 30 分钟，核心接口可用请求数 / 总请求数 × 100% |
| G-08 | 治理逻辑资源开销 | 网关进程内原生实现，无额外中间件进程 | `docker compose ps` 确认无独立限流/熔断中间件容器；网关进程内存增量 ≤ 20MB（治理模块启用前后对比） |

### 2.3 服务发现与负载均衡指标

| 编号 | 指标名称 | 达标阈值 | 测量方法 |
|---|---|---|---|
| S-01 | 服务注册方式 | 服务启动时自动注册至 etcd | 启动测试服务后，etcd 中可查询到对应实例 key，延迟 ≤ 3s |
| S-02 | 服务下线感知 | 实例停止后网关自动剔除 | 停止一个服务实例，网关在 ≤ 10s 内不再向其转发请求 |
| S-03 | 健康检查 | 支持主动健康检查，异常实例自动摘除 | 对实例注入故障（关闭健康检查端点），网关在 ≤ 10s 内停止转发 |
| S-04 | 负载均衡策略 | 至少支持加权轮询、一致性哈希两种 | 分别配置两种策略，验证请求分发符合策略预期 |
| S-05 | 本地 etcd 部署模式 | 单节点 | `docker compose ps` 确认 etcd 容器数量 = 1 |
| S-06 | 生产 etcd 切换能力 | 配置项切换即可改为高可用集群 | 修改配置指向三节点 etcd 集群地址，网关无需改代码即可正常服务发现 |

### 2.4 全链路追踪指标

| 编号 | 指标名称 | 达标阈值 | 测量方法 |
|---|---|---|---|
| T-01 | TraceId 透传覆盖率 | 100%（网关→服务→数据库全链路） | 随机抽取 100 笔请求，每笔请求的网关日志、服务日志、数据库慢查询日志中均可检索到同一 TraceId |
| T-02 | 本地链路输出方式 | 控制台直接打印 | 启动网关后，终端可实时看到每笔请求的 TraceId 与跨度信息 |
| T-03 | Jaeger 对接（可选） | 支持对接轻量 Jaeger 实例 | 配置 Jaeger endpoint 后，Jaeger UI 可查询到完整调用链 |
| T-04 | 本地测试服务覆盖数 | ≥ 5 个 | 本地环境启动 ≥ 5 个测试微服务，全部接入 TraceId 透传 |
| T-05 | 问题定位效率提升 | ≥ 60% | 对比无追踪时人工排查平均耗时（基线值，需在项目启动前实测记录）与有追踪时平均耗时，提升比例 = (基线耗时 - 追踪后耗时) / 基线耗时 × 100% |
| T-06 | 生产扩展能力 | 可平滑扩展至 ≥ 10 个业务服务 | 接入第 10 个服务时，网关无需改代码，仅需配置路由规则 |

### 2.5 配置热更新指标

| 编号 | 指标名称 | 达标阈值 | 测量方法 |
|---|---|---|---|
| C-01 | 热更新配置项 | 路由配置、限流规则、熔断策略三类 | 分别修改三类配置，验证均无需重启网关即生效 |
| C-02 | 热更新生效延迟 | ≤ 5s | 从配置写入到网关实际按新规则处理请求的时间差 |
| C-03 | 热更新期间请求连续性 | 0 笔请求因配置更新失败或断开 | 配置更新期间持续发送 1000 QPS 流量，错误率仍 < 0.01% |
| C-04 | 本地配置存储 | SQLite（默认） | 本地环境 `docker compose` 启动后，配置数据存储于 SQLite 文件，无独立数据库容器 |
| C-05 | 生产配置存储切换 | 可无缝切换为 MySQL | 修改配置存储驱动为 MySQL，网关无需改代码即可读写配置 |

### 2.6 部署与资源指标

| 编号 | 指标名称 | 达标阈值 | 测量方法 |
|---|---|---|---|
| D-01 | 本地一键启动 | `docker compose up` 一条命令启动全部组件 | 执行命令后 60s 内所有容器状态为 healthy |
| D-02 | 本地组件清单 | 网关 + ≥ 3 个测试服务 + etcd + Redis + 可观测组件 | `docker compose ps` 逐一核对 |
| D-03 | 本地全套环境总内存 | ≤ 5.5 GB（设计上限 6 GB） | 全部容器启动并稳定运行 5 分钟后，`docker stats` 汇总所有容器内存使用量 |

| D-06 | 生产可观测 | Prometheus 采集 QPS、延迟、错误率 | Prometheus 中可查询到网关暴露的 `gateway_qps_total`、`gateway_request_duration_seconds`、`gateway_error_rate` 指标 |

## 3. 项目范围界定

### 3.1 核心范围（必须做）

以下为项目必须交付的功能模块，缺一不可：

| 编号 | 模块 | 必须交付的具体能力 |
|---|---|---|
| M-01 | 网关核心路由引擎 | ① 动态路由配置（路径 + Method 匹配）② 路径重写 ③ 请求拦截（前置处理）④ 响应拦截（后置处理）⑤ 单实例 ≥ 10000 QPS 转发能力 |
| M-02 | 服务注册与发现 | ① 基于 etcd 的服务自动注册 ② 实例自动上下线感知 ③ 主动健康检查与异常摘除 ④ 加权轮询负载均衡 ⑤ 一致性哈希负载均衡 |
| M-03 | 流量治理 | ① 令牌桶限流（接口级）② 漏桶限流（接口级）③ 熔断器（错误率/慢调用触发 + 半开恢复）④ 按比例灰度发布 ⑤ 流量染色（Header/用户标识） |
| M-04 | 全链路追踪 | ① OpenTelemetry 集成 ② TraceId 生成与透传（网关→服务→数据库）③ 本地控制台链路信息打印 ④ 可选 Jaeger 对接 |
| M-05 | 管理后台接口 | ① 路由配置 CRUD 接口 ② 限流规则 CRUD 接口 ③ 熔断策略 CRUD 接口 ④ 配置热更新（≤ 5s 生效，无需重启） |
| M-06 | 本地开发环境 | ① Docker Compose 一键编排 ② 网关 + ≥ 3 测试服务 + etcd（单节点）+ Redis + 可观测组件 ③ 总内存 ≤ 5.5GB ④ SQLite 配置存储 |
| M-07 | 生产部署支持 | ① K8s Deployment/Service/HPA 清单 ② MySQL 配置存储切换 ③ etcd 高可用集群切换 ④ Prometheus 指标暴露（QPS/延迟/错误率） |

### 3.3 排除范围（明确不做）

以下内容**不在本项目范围内**，后续需求变更需单独评审：

| 编号 | 排除项 | 排除理由 |
|---|---|---|
| E-01 | 身份认证与授权（OAuth2 / JWT / API Key 校验） | 原始描述未提及，认证授权属于独立安全模块，不在本次基线内 |
| E-02 | 管理后台前端界面 | 仅提供管理后台 REST 接口，不开发可视化前端页面 |
| E-03 | API 聚合 / BFF 层编排 | 网关仅做透明转发与流量治理，不做多服务数据聚合、字段裁剪等 BFF 能力 |
| E-04 | WebSocket / gRPC 长连接代理 | 仅支持 HTTP/HTTPS 请求转发，不处理长连接协议 |
| E-05 | 多租户与计费系统 | 不做租户隔离、用量统计、配额计费等商业化能力 |
| E-06 | 本地 etcd 三节点集群 | 本地开发明确采用单节点模式以降低资源开销，三节点仅在生产环境配置 |
| E-07 | 本地完整可观测技术栈 | 本地仅控制台打印 + 可选轻量 Jaeger，不部署完整 Prometheus + Grafana + AlertManager 集群（Prometheus 指标暴露能力保留） |
| E-08 | 消息队列 / 异步处理 | 网关同步转发，不引入 MQ 做异步削峰或事件驱动 |
| E-09 | 插件化扩展机制（WASM / Lua 脚本） | 治理逻辑原生 Go 实现，不提供第三方插件运行时 |
| E-10 | 跨数据单元 / 多集群网关联邦 | 单集群部署，不做多活、异地多活网关协同 |

## 4. 约束条件

### 4.1 技术栈约束

| 编号 | 约束项 | 具体要求 | 违反判定 |
|---|---|---|---|
| TC-01 | 编程语言 | Go 1.22，不得使用其他语言编写网关核心逻辑 | `go.mod` 中 `go 1.22`，核心包无 cgo 依赖外部非 Go 库 |
| TC-02 | Web 框架 | Gin，不得替换为 Echo / Fiber / net/http 裸写 | `go.mod` 包含 `github.com/gin-gonic/gin` |
| TC-03 | 服务发现 | etcd，本地单节点，不得替换为 Consul / Nacos / Eureka | 服务注册模块仅依赖 etcd client |
| TC-04 | 缓存 | Redis，用于限流计数 / 熔断状态共享等场景 | `docker-compose.yml` 包含 redis 服务 |
| TC-05 | 配置存储 | 本地 SQLite，生产可切换 MySQL，不得使用 MongoDB / PostgreSQL 等其他数据库 | 配置存储层通过驱动抽象，仅实现 SQLite 与 MySQL 两种驱动 |
| TC-06 | 限流算法 | 令牌桶 + 漏桶，必须两种均实现，不得只实现一种 | 代码中存在两种算法的独立实现类，配置可切换 |
| TC-07 | 熔断模式 | 熔断器模式（关闭→打开→半开→关闭状态机），不得用简单重试代替 | 熔断状态机单元测试覆盖全部状态转移路径 |
| TC-08 | 链路追踪 | OpenTelemetry，不得替换为 Zipkin Brave / SkyWalking 私有 SDK | 依赖 `go.opentelemetry.io/otel` 系列包 |
| TC-09 | 指标采集 | Prometheus，网关暴露 `/metrics` 端点 | 端点返回 Prometheus 文本格式，包含 QPS / 延迟 / 错误率指标 |
| TC-10 | 容器编排（本地） | Docker Compose，不得要求本地安装 K8s / Minikube | 本地启动仅需 `docker compose up` |
| TC-11 | 生产编排 | Kubernetes（Deployment + Service + HPA） | 提供可直接 apply 的 YAML 清单 |
