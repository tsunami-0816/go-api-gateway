#### 1.2.2 modernc.org/sqlite 与 CGO_ENABLED=0 兼容性（P0-1 修复核心）

`modernc.org/sqlite` 是 SQLite C 源码经 `ccgo` 翻译为纯 Go 的实现，**不依赖 cgo、不依赖系统 libc**。这使得：

1. 编译：`CGO_ENABLED=0 go build` 可直接通过
2. 运行：可在 `gcr.io/distroless/static-debian12:nonroot`（无 libc）中正常运行
3. 驱动注册：

```go
import (
    "gorm.io/driver/sqlite"  // GORM 的 SQLite 驱动底层使用 modernc.org/sqlite
    "gorm.io/gorm"
)
// 或显式使用 modernc
import _ "modernc.org/sqlite"
```

> 注：GORM 官方 `gorm.io/driver/sqlite` v1.5.4+ 底层已支持 `modernc.org/sqlite`，通过 build tag `sqlite_modernc` 或默认纯 Go 路径选择。生产 MySQL 使用 `gorm.io/driver/mysql`。

#### 1.2.3 SQLite ↔ MySQL 切换兼容性

通过 GORM 驱动抽象层实现，切换仅修改配置：

```yaml
# 本地
config_store:
  driver: sqlite
  dsn: "./data/gateway.db"

# 生产
config_store:
  driver: mysql
  dsn: "user:pwd@tcp(mysql-host:3306)/gateway?charset=utf8mb4&parseTime=True"
```

**SQL 兼容性约束**（P1-3 修复）：
- 不使用数据库特定函数（`IFNULL`/`NOW()`/`CONCAT`），统一用 `COALESCE` 或 GORM 方法
- 主键使用 UUID（`VARCHAR(36)`），不依赖自增，彻底规避自增语法差异
- 时间字段统一 `time.Time`，由 GORM 映射
- `updated_at` 不使用 `ON UPDATE CURRENT_TIMESTAMP`，改用 GORM `autoUpdateTime` 标签
- **不手写 DDL 初始化**：本地由 `GORM AutoMigrate` 建表；生产首次部署时由 GORM AutoMigrate 或 DBA 审核后的 DDL 脚本建表
- 不使用存储过程、触发器、视图

#### 1.2.4 etcd 版本兼容性

- 本地：etcd v3.5.15 单节点，API v3
- 生产：etcd v3.5.x 三节点集群，同大版本 API 完全兼容
- 网关通过 `go.etcd.io/etcd/client/v3` 连接，不依赖特定拓扑

#### 1.2.5 OpenTelemetry 与 Jaeger 兼容性

- OTel SDK v1.28.0 通过 OTLP 导出
- Jaeger v1.55+ 原生支持 OTLP
- 本地使用 `stdout` exporter（控制台打印）；生产切换 OTLP exporter 指向 Jaeger

## 2. 整体分层架构

### 2.1 架构分层总览

系统采用六层架构，自上而下：**接入层 → 应用层 → 服务层 → 计算层 → 存储层**，运维层为横向支撑层贯穿所有层级。

```
┌─────────────────────────────────────────────────────────────────┐
│                        接入层 (Access Layer)                      │
│  数据面 HTTP Server · 管理面 HTTP Server · 端口隔离 · 连接管理    │
├─────────────────────────────────────────────────────────────────┤
│                        应用层 (Application Layer)                 │
│  路由匹配引擎 · 请求拦截链 · 响应拦截链 · 路径重写 · 反向代理      │
│  管理API控制器                                                    │
├─────────────────────────────────────────────────────────────────┤
│                        服务层 (Service Layer)                     │
│  服务注册 · 服务发现 · 健康检查 · 负载均衡 · 流量治理执行器        │
├─────────────────────────────────────────────────────────────────┤
│                        计算层 (Computation Layer)                 │
│  双层限流引擎 · 熔断状态机(全局协调) · 灰度路由计算 · 滑动窗口     │
│  配置热更新处理器 · 一致性哈希环                                  │
├─────────────────────────────────────────────────────────────────┤
│                        存储层 (Storage Layer)                     │
│  配置存储(SQLite/MySQL) · 服务注册(etcd) · 计数缓存(Redis)        │
├─────────────────────────────────────────────────────────────────┤
│  ┌───────────────────────────────────────────────────────────┐  │
│  │                  运维层 (Operations Layer)                  │  │
│  │  日志(zap) · 指标(Prometheus) · 链路(OTel) · 告警 · 部署   │  │
│  └───────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 各层职责与组件详解

#### 2.2.1 接入层（Access Layer）

| 组件 | 职责 | 技术实现 |
|---|---|---|
| 数据面 HTTP Server | 接收客户端业务请求并转发 | Gin Engine（监听 0.0.0.0:8080） |
| 管理面 HTTP Server | 配置 CRUD 接口 | Gin Engine（监听 0.0.0.0:8081） |
| 指标端点 | Prometheus 指标采集 | `/metrics`（8081） |
| 健康检查端点 | K8s 探针 | `/healthz`、`/readyz`（8081） |
| 连接管理器 | 最大连接数、超时、Keep-Alive | net/http Server 参数 |

**端口隔离设计**（P1-8 修复）：

| 端口 | 用途 | 容器内绑定 | 宿主机映射（本地 compose） | 说明 |
|---|---|---|---|---|
| 8080 | 数据面（业务转发） | 0.0.0.0:8080 | `8080:8080` | 对外暴露 |
| 8081 | 管理面（API+指标+健康） | 0.0.0.0:8081 | `127.0.0.1:8081:8081` | 仅宿主机回环可访问，局域网不可达 |

> 关键决策：容器内管理面绑 `0.0.0.0`（使 Docker 端口映射生效），但通过宿主机回环映射 `127.0.0.1:8081:8081` 保证安全性。生产环境通过 K8s NetworkPolicy 限制访问源。

#### 2.2.2 应用层（Application Layer）

| 组件 | 职责 | 技术实现 |
|---|---|---|
| 路由匹配引擎 | Path + Method 匹配规则 | Gin radix tree + 自定义规则缓存 |
| 请求拦截链 | Trace注入→限流→熔断→灰度→路径重写→日志 | Gin Middleware 链 |
| 响应拦截链 | 指标采集→熔断统计→日志→Span结束 | Gin 后置钩子 |
| 路径重写器 | 正则替换 + 前缀截断 | 自定义 Rewriter |
| 反向代理器 | 转发至后端实例 | `httputil.ReverseProxy` 定制 |
| 管理API控制器 | 路由/限流/熔断/灰度 CRUD | Gin Handler + Service |
| 重试执行器 | 失败请求重试（仅幂等方法） | 自定义 RetryHandler（P2-3） |

**请求处理流水线**：

```
客户端请求
  ▼
[接入层] 接收解析
  ▼
[应用层-拦截链] Trace注入 → 限流检查(本地双层) → 熔断检查 → 灰度判定 → 路径重写
  ▼
[服务层] 服务发现(本地缓存) → 过滤不健康 → 负载均衡(加权轮询/一致性哈希)
  ▼
[反向代理] 构建请求 → 注入traceparent → 转发后端（含重试）
  ▼
[应用层-响应链] 指标采集 → 熔断统计 → 日志 → Span结束
  ▼
响应返回客户端
```

#### 2.2.3 服务层（Service Layer）

| 组件 | 职责 | 技术实现 |
|---|---|---|
| 服务注册器 | 服务启动注册至 etcd | etcd client v3 + Lease（TTL=10s） |
| 服务发现器 | 订阅实例变更 | etcd Watch + 本地 atomic.Value 缓存 |
| 健康检查器 | 主动探测，异常摘除 | 定时 HTTP GET /health |
| 负载均衡器 | 选择目标实例 | 加权轮询 / 一致性哈希（带权） |
| 限流执行器 | 接口级限流 | 调用计算层双层限流引擎 |
| 熔断器 | 下游故障快速失败 | 计算层熔断状态机（全局协调） |
| 灰度路由器 | 按比例/染色路由版本 | 加权随机 / Header匹配 |

**负载均衡策略设计**（P2-2 修复-一致性哈希）：

| 策略 | 实现要点 |
|---|---|
| 加权轮询（WRR） | 经典平滑加权轮询（nginx 算法），按权重分配请求 |
| 一致性哈希（CH） | ① 哈希算法：murmur3（32bit）② 虚拟节点倍数：150 ③ 总虚拟节点数 = Σ(实例权重 × 150) ④ 每个实例按权重比例分配虚拟节点 ⑤ 请求 key（IP/指定Header）哈希后在环上顺时针查找最近虚拟节点 ⑥ 实例上下线时重建环（影响约 1/N 的请求） |

#### 2.2.4 计算层（Computation Layer）

| 组件 | 职责 | 技术实现 |
|---|---|---|
| 双层限流引擎 | 本地令牌桶/漏桶 + Redis 批量预取 | 见 3.4 节（P0-2 修复） |
| 熔断状态机 | Closed→Open→HalfOpen | 见 3.5 节（P1-1 修复，全局协调） |
| 滑动窗口统计器 | 错误率/慢调用比例 | 本地时间轮+环形缓冲区（熔断判断依据） |
| 灰度路由计算器 | 哈希/随机判定版本 | murmur3 哈希取模 |
| 配置热更新处理器 | 监听变更，原子替换快照 | etcd Watch + atomic.Value |
| 一致性哈希环 | 带权虚拟节点环 | 见 2.2.3 |

#### 2.2.5 存储层（Storage Layer）

| 存储组件 | 存储内容 | 访问模式 | 本地 | 生产 |
|---|---|---|---|---|
| SQLite / MySQL | 路由/限流/熔断/灰度配置 | 管理面读写 + 数据面读 | 嵌入式单文件 | MySQL 主从 |
| etcd | 服务实例注册 | 写(注册)+读/Watch(发现) | 单节点 | 三节点集群 |
| Redis | 限流预取令牌/熔断全局状态/灰度计数 | 低频同步读写 + Lua | 单节点 | 主从+哨兵 |

#### 2.2.6 运维层（Operations Layer）

| 组件 | 职责 | 技术实现 |
|---|---|---|
| 日志系统 | 结构化日志含 TraceId | zap + 异步写入 |
| 指标系统 | QPS/延迟/错误率等 | prometheus/client_golang |
| 链路追踪 | TraceId 生成透传、Span | OpenTelemetry Go SDK |
| 健康检查 | 存活/就绪探针 | 自定义 HealthIndicator（P1-7 修复） |
| 配置管理 | 多源配置热加载 | viper |
| 部署编排 | Compose / K8s | YAML 清单 |

## 3. 核心业务链路

### 3.1 业务链路总览

| 编号 | 链路名称 | 触发方 | 核心节点 |
|---|---|---|---|
| FL-01 | HTTP 请求转发链路 | 客户端 | 接入→拦截链→路由→服务发现→负载均衡→反向代理(含重试)→响应拦截 |
| FL-02 | 服务注册与发现链路 | 后端服务 | 启动→etcd注册(Lease)→网关Watch→本地缓存→健康检查 |
| FL-03 | 限流执行链路（双层） | 网关数据面 | 请求→本地令牌桶(纳秒级)→后台协程批量预取Redis→降级本地模式 |
| FL-04 | 熔断执行链路（全局协调） | 网关数据面 | 状态检查→本地滑动窗口统计→状态转移→半开全局计数→事件广播 |
| FL-05 | 灰度发布链路 | 网关数据面 | 染色判定→哈希比例计算→版本过滤 |
| FL-06 | 配置热更新链路 | 管理面 | 写入DB→etcd事件→网关Watch→全量拉取→原子替换快照 |
| FL-07 | 全链路追踪链路 | 网关数据面 | TraceId生成→Span→上下文透传→服务继承→DB注释注入→输出 |

### 3.2 FL-01：HTTP 请求转发链路

```
客户端              网关数据面(8080)                  后端服务
  │                    │                               │
  │ ① HTTP Request     │                               │
  │───────────────────>│                               │
  │                    │ ② Trace中间件：提取/生成TraceId│
  │                    │ ③ 限流：本地令牌桶扣减(无网络) │
  │                    │    ├ 被限流 → 429             │
  │                    │    └ 通过 → 继续              │
  │                    │ ④ 熔断：读取熔断器状态         │
  │                    │    ├ Open → 503 快速失败      │
  │                    │    └ HalfOpen/Closed → 继续   │
  │                    │ ⑤ 灰度：染色判定+哈希比例      │
  │                    │ ⑥ 路由匹配(radix tree)+重写    │
  │                    │ ⑦ 服务发现(本地缓存,无网络)    │
  │                    │ ⑧ 负载均衡(WRR/CH)选实例       │
  │                    │ ⑨ 反向代理转发(含重试)         │
  │──────────────────────────────────────────────────>│
  │                    │ ⑩ 响应拦截：指标+熔断统计+日志  │
  │ <──────────────────│                               │
```

**各节点输入/处理/输出**：

| 节点 | 输入 | 处理逻辑 | 输出 |
|---|---|---|---|
| ② Trace注入 | traceparent Header | 存在则提取上下文，不存在生成新 TraceId；创建 SERVER Span | 上下文注入 Context；TraceId 写响应 Header |
| ③ 限流 | Path+Method+IP | 匹配限流规则；调用本地双层限流引擎（见 FL-03） | 放行/429 |
| ④ 熔断 | 目标服务+路由ID | 读熔断器状态（本地优先，Redis 同步） | 放行/503 |
| ⑤ 灰度 | Header/Cookie/IP | 染色匹配优先，否则哈希比例判定 | 版本标签 stable/canary |
| ⑥ 路由匹配 | Path+Method | radix tree 匹配 → 路径重写 → 目标服务 | 路由配置+重写后Path |
| ⑦ 服务发现 | 服务名+版本 | 本地缓存过滤不健康实例+按版本过滤 | 健康实例列表 |
| ⑧ 负载均衡 | 实例列表+策略 | WRR 或 CH 选择 | 目标实例 Address |
| ⑨ 反向代理 | 原始请求+地址 | 构建请求、注入 traceparent、设置超时、转发；失败按策略重试 | 后端响应 |
| ⑩ 响应拦截 | 响应+上下文 | 记录延迟直方图、状态码计数、熔断滑动窗口、访问日志、结束 Span | 最终响应 |

**重试机制设计**（P2-3 修复）：

| 设计项 | 规则 |
|---|---|
| 重试触发 | 路由 `retry_count > 0` 且响应状态码命中 `retry_on_status`（默认 502,503,504）或网络错误 |
| 实例选择 | 重试时**排除已失败实例**，重新从健康列表选择（避免同一实例反复失败） |
| 超时约束 | 重试总耗时不超过路由 `timeout_ms`，超出则放弃重试返回最后一次结果 |
| 幂等限制 | 默认仅对幂等方法（GET/HEAD/OPTIONS/PUT/DELETE）重试；非幂等（POST）不重试，除非路由显式配置 `retry_non_idempotent=true` |
| 熔断统计 | 重试的每次结果（成功/失败）均计入熔断滑动窗口统计 |
| 最大重试 | `retry_count` 默认 0（不重试），最大 3 |

### 3.3 FL-02：服务注册与发现链路

**服务注册（后端服务侧）**：

```
服务启动 → 连接etcd → 创建Lease(TTL=10s) → 注册Key /services/{name}/{id}
  → Value={address,weight,metadata{version},register_time} → 绑定Lease
  → KeepAlive协程(每5s续约) → 正常运行
  → 服务关闭 → 撤销Lease → Key自动过期
```

**服务发现（网关侧）**：

```
网关启动 → 连接etcd → 全量拉取 /services/ 前缀构建初始缓存
  → Watch /services/ 前缀(PUT/DELETE事件) → 事件更新本地缓存
  → atomic.Value 原子替换缓存(读无锁) → 健康检查协程(每10s探测/health)
  → 连续2次失败标记Unhealthy剔除 → 连续2次成功恢复Healthy
```

**关键参数**：Lease TTL=10s；KeepAlive=5s；健康检查间隔=10s；失败/恢复阈值=2次；下线感知≤10s。

### 3.4 FL-03：限流执行链路（双层架构，P0-2 修复核心）

**架构原则**：请求路径只操作本地内存（纳秒级），Redis 仅用于多实例间令牌批量预取与全局协调。Redis 调用频率从 10000 次/s 降至每实例 10 次/s。

**令牌桶双层流程**：

```
请求到达
  ▼
① 匹配限流规则(route-id, algorithm=token_bucket, rate, capacity)
  ▼
② 操作本地令牌桶(内存, 无网络):
   - 计算自上次补充至今应补充的令牌数 = elapsed × rate
   - tokens = min(capacity, tokens + refill)
   - 若 tokens >= 1: tokens -= 1, 放行
   - 若 tokens < 1: 拒绝, 返回 429
  ▼
③ 后台同步协程(每100ms执行, 与请求路径解耦):
   - 计算本地令牌桶消耗速率
   - 从 Redis 全局桶批量预取令牌到本地:
     * 预取量 = rate × 0.1s × 预取系数(默认2)
     * Lua 脚本原子扣减全局桶并返回实际预取量
     * 若全局桶不足, 预取剩余量
   - 若 Redis 不可用: 本地令牌桶独立运行(降级模式, 精度下降)
  ▼
④ Redis 全局桶补充(每1s执行):
   - 按 rate 向全局桶补充令牌, 不超过 capacity
   - Lua 脚本保证原子性
```

**漏桶双层流程**：

```
请求到达
  ▼
① 操作本地漏桶(内存):
   - 漏水: elapsed × rate, current_level = max(0, level - leaked)
   - 若 level < capacity: level += 1, 放行
   - 否则拒绝 429
  ▼
② 后台同步(每100ms): 与 Redis 全局水位对齐(批量同步)
```

**Redis 批量预取 Lua 脚本伪代码**：

```lua
-- KEYS[1] = ratelimit:{route-id}:token_bucket:global
-- ARGV[1] = rate, ARGV[2] = capacity, ARGV[3] = prefetch_amount, ARGV[4] = now
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens') or 0)
local last_refill = tonumber(redis.call('HGET', KEYS[1], 'last_refill_time') or 0)
local refill = math.floor((tonumber(ARGV[4]) - last_refill) * tonumber(ARGV[1]) / 1000)
tokens = math.min(tonumber(ARGV[2]), tokens + refill)
local fetched = math.min(tokens, tonumber(ARGV[3]))
tokens = tokens - fetched
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'last_refill_time', ARGV[4])
redis.call('EXPIRE', KEYS[1], 3600)  -- P1-4: 刷新TTL=1h
return fetched
```

**降级策略**：

| 场景 | 行为 |
|---|---|
| Redis 正常 | 双层模式，本地预取令牌，精度高 |
| Redis 不可用 | 自动切换纯本地模式，限流继续生效（多实例近似），恢复后自动切回 |
| 本地令牌耗尽且 Redis 预取失败 | 按本地剩余令牌放行，不阻塞请求 |

**响应 Header**：`X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-RateLimit-Reset`、`Retry-After`

### 3.5 FL-04：熔断执行链路（全局协调，P1-1 修复）

**设计原则**：熔断判断基于本地滑动窗口（性能优先）；半开探测请求数通过 Redis 全局计数避免放大；熔断状态变更通过 Redis 发布事件广播同步。

```
请求到达(目标服务/路由)
  ▼
① 读取熔断器状态: 本地缓存优先(Redis 同步), 三态 CLOSED/OPEN/HALF_OPEN
  │
  ├─ CLOSED(正常)
  │    ▼
  │  ② 放行, 记录到本地滑动窗口(时间轮+环形缓冲区, 10s/10桶)
  │    ▼
  │  ③ 统计: 总请求数、错误率、慢调用比例
  │    ▼
  │  ④ 触发条件(任一满足): 总请求≥min(20) AND (错误率≥50% OR 慢调用比例≥60%)
  │    ├ 满足 → 状态转 OPEN, 写Redis+发布事件, 记录打开时间
  │    └ 不满足 → 保持 CLOSED
  │
  ├─ OPEN(熔断中)
  │    ▼
  │  ⑤ 快速失败 503, Header: X-Circuit-Breaker: open
  │    ▼
  │  ⑥ 到达熔断超时(30s) → 状态转 HALF_OPEN, 写Redis+发布事件
  │
  └─ HALF_OPEN(半开探测)
       ▼
       ⑦ Redis 原子递增全局半开探测计数(INCR circuit:{svc}:{route}:halfopen_count)
          对比阈值 half_open_max_requests(5):
            - count <= 5: 放行探测请求
            - count > 5: 快速失败
       ▼
       ⑧ 探测请求结束统计:
          - 全部成功 → 状态转 CLOSED, 重置统计与全局计数, 发布事件
          - 任一失败 → 状态转 OPEN, 重新计时, 发布事件
```

**多实例一致性保证**（P1-1 方案 A）：

| 维度 | 本地 | Redis（全局） |
|---|---|---|
| 滑动窗口统计 | ✅ 本实例独立统计 | ❌ 不参与判断（P2-9 修复） |
| 熔断触发判断 | ✅ 基于本地窗口 | ❌ |
| 半开探测计数 | ❌ | ✅ `INCR` 全局计数，防止探测数放大 |
| 熔断状态读写 | ✅ 本地缓存(读优先) | ✅ 状态变更时 SET + 发布事件 |
| 状态同步 | ✅ 订阅 Redis 事件更新本地 | - |

**熔断策略参数**：

| 参数 | 默认值 |
|---|---|
| 滑动窗口大小 | 10s |
| 最小请求数 | 20 |
| 错误率阈值 | 50% |
| 慢调用延迟阈值 | 1s |
| 慢调用比例阈值 | 60% |
| 熔断超时 | 30s |
| 半开探测请求数 | 5（全局） |

### 3.6 FL-05：灰度发布链路

```
请求到达 → 检查灰度规则
  ▼
① 染色判定(最高优先级): 遍历 stain_rules
   - Header/Cookie/Query 精确匹配 / UserID IN 列表
   ├ 命中 → 100% 路由灰度版
   └ 未命中 → 继续
  ▼
② 比例判定: hash_key 默认客户端IP, hash_value = murmur3(key) % 100
   ├ hash_value < gray_percent → 灰度版
   └ hash_value >= gray_percent → 稳定版
  ▼
③ 版本标签写入上下文, 服务发现按 Metadata.version 过滤实例
```

**灰度比例精度验证**（P2-5 修复）：基线 G-05 验证必须使用 ≥100 个不同 `X-Forwarded-For` 值模拟多用户，否则单 IP 哈希导致比例失真。1000 笔请求中灰度版接收量预期 180-220（18%-22%）。

### 3.7 FL-06：配置热更新链路

```
管理API修改配置 → Token鉴权+校验 → 写入SQLite/MySQL
  → 记录gw_operation_log + gw_config_version(变更快照)
  → 发布etcd事件 /config/changes/{type}/{ts} (TTL=60s)
  → 网关Watch接收 → 全量拉取对应类型配置 → 构建不可变快照
  → atomic.Value 原子替换(读无锁, 0失败) → 新配置生效(≤5s)
  → 日志记录 config reloaded
```

**兜底**：每 60s 定时全量同步，即使 Watch 事件丢失也能收敛。

### 3.8 FL-07：全链路追踪链路

**采样策略**（P2-4 修复）：

| 环境 | TraceId 生成 | Span 采样 | 说明 |
|---|---|---|---|
| 本地 | 100% | 全量采样（异步日志输出） | 基线 T-02 控制台打印 |
| 生产 | 100% | 默认 10%（可配置）；5xx 错误强制采样 | 控制开销，错误全保留 |

> TraceId 必须 100% 生成透传（基线 T-01），采样仅控制 Span 是否上报导出器，不影响 TraceId 透传与日志记录。

**链路**：网关生成/提取 TraceId → 创建 SERVER Span → 注入 traceparent Header → 后端服务提取创建子 Span → DB 操作时 SQL 注释 `/* trace_id=xxx */` 注入 → Span 结束 → 本地 stdout / 生产 OTLP→Jaeger。

**逻辑删除设计**（P1-2 修复核心）：
- `deleted_at` 为 NULL 表示未删除，有值表示已删除（记录删除时间）
- 唯一索引包含 `deleted_at`：MySQL/SQLite 中 NULL 不参与唯一约束比较
- 因此多条已删除记录（`deleted_at` 各不相同）不会冲突，同一时刻最多一条 `deleted_at=NULL`（未删除记录唯一）
- GORM 模型使用 `gorm.DeletedAt` 类型自动实现

**命名规范**：表名小写蛇形 `gw_` 前缀；字段小写蛇形；索引 `idx_{表}_{字段}`、唯一 `uk_{表}_{字段}`；时间存 UTC。

### 4.4 etcd 数据模型

| Key 模式 | 用途 | Value |
|---|---|---|
| `/services/{name}/{instance-id}` | 服务实例注册 | `{address, weight, metadata{version}, register_time}` + Lease(TTL=10s) |
| `/config/changes/{type}/{timestamp}` | 配置变更事件 | `{config_type, action, config_id, updated_at}` TTL=60s |

### 4.5 Redis 数据模型（P1-4/P2-9 修复）

| Key 模式 | 类型 | 用途 | TTL |
|---|---|---|---|
| `ratelimit:{route-id}:{alg}:{dim}:global` | Hash | 限流全局桶（tokens/last_refill_time 或 level/last_leak_time） | **每次 Lua 执行后 EXPIRE 刷新为 3600s**（P1-4） |
| `circuit:{service}:{route}:state` | String | 熔断器状态：closed/open/half_open | open 状态带 TTL=open_duration_ms；其余持久但定期清理 |
| `circuit:{service}:{route}:halfopen_count` | String | **全局半开探测计数**（P1-1） | TTL=open_duration_ms |
| `circuit:{service}:{route}:stats` | Hash | 熔断滑动窗口统计（仅多实例聚合查询，**不参与熔断判断**，P2-9） | 滑动窗口自动过期 |

> 本地限流状态（每实例令牌桶）存在网关进程内存，不入 Redis。熔断滑动窗口统计存在本地内存，作为熔断判断依据；Redis stats key 仅用于管理面聚合查询。

## 5. 接口规范定义

### 5.1 统一 API 规范

| 约定项 | 规范 |
|---|---|
| 协议 | HTTP/1.1 + HTTPS（生产） |
| 数据格式 | JSON（`application/json; charset=utf-8`） |
| 编码 | UTF-8 |
| 时间 | ISO 8601 UTC：`2026-10-04T10:00:00Z` |
| 命名 | 路径 kebab-case；字段 snake_case |
| 版本 | URL 前缀 `/api/v1/` |
| 分页 | `page`(从1) + `page_size`(默认20, 最大100) |

### 5.2 统一响应格式

**成功**：
```json
{ "code": 0, "message": "success", "data": {...}, "trace_id": "..." }
```

**分页成功**：
```json
{ "code": 0, "message": "success",
  "data": { "list": [...], "pagination": { "page":1, "page_size":20, "total":156, "total_pages":8 } },
  "trace_id": "..." }
```

**失败**：
```json
{ "code": 40101, "message": "路由路径已存在", "data": null, "trace_id": "...",
  "errors": [ { "field": "path", "message": "..." } ] }
```

### 5.3 错误码规范

```
4  01  01
│  │   └─ 错误序号(01-99)
│  └───── 模块(00通用,01路由,02限流,03熔断,04灰度,05服务,09系统)
└──────── HTTP大类(4客户端,5服务端)
```

**通用错误码**：0 成功；40000 参数错误；40001 校验失败；40100 未授权；40300 禁止；40400 不存在；40900 冲突；42900 频繁；50000 内部错误；50001 DB 失败；50002 热更新失败；50300 依赖不可用。

**业务错误码**：40101 路由路径+方法已存在；40102 目标服务不存在；40103 路由不存在；40201 限流算法不支持；40202 rate 必须>0；40301 错误率阈值1-100；40401 灰度比例0-100；40501 服务名已存在。

### 5.4 鉴权规则

#### 5.4.1 管理面鉴权（P2-6 修复：操作人区分）

**请求 Header**：
```
Authorization: Bearer {admin-token}
X-Operator: {username}    # 可选，兜底操作人标识
```

**Token 配置**（支持多 Token 映射操作人）：
```yaml
admin:
  auth:
    enabled: true
    tokens:
      - token: "${GATEWAY_ADMIN_TOKEN_ALICE}"
        username: "alice"
      - token: "${GATEWAY_ADMIN_TOKEN_BOB}"
        username: "bob"
    # 兼容单一 token 配置
    # token: "${GATEWAY_ADMIN_TOKEN}"
    # default_username: "admin"
```

**操作人解析优先级**：① Token 映射的 username → ② `X-Operator` Header → ③ default_username。`gw_operation_log.operator` 与 `gw_config_version.operator` 记录解析出的操作人。

**网络防护**：管理面 8080 端口本地映射到宿主机回环；生产通过 K8s NetworkPolicy 限制运维命名空间访问。

#### 5.4.2 数据面鉴权

数据面 8080 不做鉴权（基线 E-01），透传至后端，由后端处理。

### 5.5 核心接口清单

**路由管理**：POST/GET(list)/GET(id)/PUT/DELETE/PATCH status `/api/v1/routes[/{id}...]`

**限流规则**：POST/GET/GET(id)/PUT/DELETE/PATCH status `/api/v1/rate-limits[/{id}...]`

**熔断策略**：POST/GET/GET(id)/PUT/DELETE `/api/v1/circuit-breakers[/{id}...]`；GET state、POST reset

**灰度发布**：POST/GET/GET(id)/PUT/DELETE `/api/v1/gray-releases[/{id}...]`；PATCH percent

**服务管理**：POST/GET/GET(name)/GET instances/PUT(name)/DELETE(name) `/api/v1/services...`

**系统运维**（5.4.6 节详述）：`/healthz`、`/readyz`、`/metrics`、POST reload、GET config、GET stats

#### 6.3.3 健康检查设计（P1-7 修复）

`/healthz`（liveness）：始终返回 200（进程存活即健康）。

`/readyz`（readiness）分两阶段：

| 阶段 | 条件 | 检查内容 |
|---|---|---|
| 启动就绪（进程启动后 60s 内） | 依赖初始连接 | 配置加载完成、etcd/Redis 初始连接成功、DB 连接成功 |
| 运行时就绪（启动 60s 后） | 仅进程内部状态 | 配置快照非空、HTTP Server 正常；**不检查外部依赖实时连通性** |

> 外部依赖（etcd/Redis）短暂故障时通过降级机制继续服务，不触发摘流，避免级联震荡。依赖故障通过告警通知运维处理。

#### 6.3.4 Prometheus Adapter 部署（P1-5 修复）

HPA 自定义指标 `gateway_qps_per_pod` 需通过 Prometheus Adapter 注册到 `custom.metrics.k8s.io`：

    spec:

            - --prometheus-url=http://prometheus.monitoring:9090
            - --config=/etc/adapter/config.yaml
          volumeMounts: [ {name: config, mountPath: /etc/adapter} ]

        - name: config
          configMap: { name: prometheus-adapter-config }
---

metadata: { name: prometheus-adapter-config, namespace: monitoring }

  config.yaml: |
    rules:
      - seriesQuery: 'gateway_qps_total{job="gateway"}'
        resources: { overrides: { pod: { resource: pod } } }
        name: { matches: "gateway_qps_total", as: "gateway_qps_per_pod" }
        metricsQuery: 'sum(rate(<<.Series>>{<<.LabelMatchers>>}[1m])) by (<<.GroupBy>>)'

#### 6.3.5 网关启动初始化顺序（P2-7 修复）

```
① 加载配置文件(config.yaml + 环境变量)
② 初始化日志(zap)
③ 连接配置存储(SQLite/MySQL) → AutoMigrate 建表
④ 全量加载配置快照(路由/限流/熔断/灰度)
⑤ 连接 etcd → 全量拉取服务实例 → 启动 Watch
⑥ 连接 Redis → 启动限流同步协程(100ms)

⑨ 启动数据面 HTTP Server(8080)  ← 最后启动
/readyz 在 ①~⑧ 完成前返回不健康
```

数据面最后启动确保请求到来时所有依赖就绪。

## 7. 监控与运维

### 7.1 监控指标体系

#### 7.1.1 指标分类总览（P2-1 修复：对齐基线指标名）

| 类别 | 指标名称 | 类型 | 说明 | 基线 |
|---|---|---|---|---|
| 流量 | `gateway_qps_total` | Counter | 总请求数，按 route/service/method/status 标签 | D-06 |
| 延迟 | `gateway_request_duration_seconds` | Histogram | 请求延迟分布 | D-06 |
| 错误 | `gateway_error_rate` | Gauge | 错误率（计算值） | D-06 |
| 限流 | `gateway_rate_limit_total`/`_passed`/`_rejected` | Counter | 限流统计 | - |
| 熔断 | `gateway_circuit_breaker_state`(Gauge)/`_open_total`(Counter)/`_rejected_total`(Counter) | - | 熔断状态与次数 | - |
| 灰度 | `gateway_gray_requests_total` | Counter | 按 route/version 统计 | - |
| 服务发现 | `gateway_service_instances`(Gauge)/`_discovery_events_total`(Counter) | - | 实例数与事件 | - |
| 系统 | `gateway_memory_usage_bytes`/`gateway_goroutines`/`gateway_active_connections`/`gateway_config_reload_total`/`gateway_config_reload_duration_seconds` | - | 进程与配置 | P-04 |

> 基线 D-06 要求的 `gateway_qps_total`、`gateway_request_duration_seconds`、`gateway_error_rate` 三个指标已对齐。

#### 7.1.2 核心 PromQL

QPS：`sum(rate(gateway_qps_total[1m])) by (route)`
P99 延迟：`histogram_quantile(0.99, sum(rate(gateway_request_duration_seconds_bucket[5m])) by (le))`
错误率：`sum(rate(gateway_qps_total{status=~"5.."}[5m])) / sum(rate(gateway_qps_total[5m])) * 100`

### 7.2 告警规则

| 级别 | 响应 | 示例 |
|---|---|---|
| P0 | 5 分钟 | 网关全部不可用、错误率 > 50% |
| P1 | 15 分钟 | 错误率 > 5%、P99 > 100ms、内存 > 100MB |
| P2 | 1 小时 | 熔断器打开、限流拒绝率 > 10%、健康实例不足 50% |
| P3 | 工作日 | 配置热更新失败、实例下线 |

核心规则：`GatewayDown`（up==0 for 1m，P0）；`GatewayHighErrorRate`（>50% for 1m，P0）；`GatewayHighLatency`（P99>0.1s for 5m，P1）；`GatewayHighMemory`（>100MB for 5m，P1）；`CircuitBreakerOpen`（P2）；`RateLimitHighRejection`（>10% for 5m，P2）；`ConfigReloadFailed`（P3）。

### 7.3 日志规范

zap 结构化 JSON，必含字段：timestamp、level、logger、message、trace_id、span_id、client_ip、method、path、route_id、target_service、target_instance、status、latency_ms、backend_latency_ms、rate_limited、circuit_state、gray_version。

**敏感字段脱敏**（CO-02）：password→`******`；token→前4后4；id_card→前6后4；phone→前3后4；email→首字符+域名；cookie/authorization→`[REDACTED]`。

### 7.4 运维流程

**配置变更**：管理API（鉴权）→ 校验 → 写DB（记 operation_log + config_version）→ 发布 etcd 事件 → 网关 Watch → 全量拉取 → 原子替换 → ≤5s 生效 → 验证/回滚。

**灰度发布**（P2-5 修复）：部署 canary 实例 → 创建灰度规则(percent=0) → 逐级 0→5→10→20→50→100，每阶段观察 5-10 分钟 → 全量稳定 30 分钟 → 下线旧版。回滚：percent 调 0。验证使用 ≥100 个不同 `X-Forwarded-For`。

**故障排查**：获取 TraceId → Jaeger 查调用链 → 网关日志过滤 → 监控指标趋势 → 定位根因 → 处置 → 验证记录。

## 8. 技术风险与应对方案

### 8.1 核心风险总览

| 编号 | 类别 | 描述 | 等级 | 应对 |
|---|---|---|---|---|
| R-01 | 性能 | 单实例 QPS 达不到 10,000 | 高 | 双层限流(本地)、异步日志、连接池、radix tree、对象池 |
| R-02 | 性能 | 平均延迟超过 2ms | 高 | 本地限流无网络、本地服务发现缓存、GOGC 调优 |
| R-03 | 性能 | 内存超过 80MB | 中 | 不可变快照、连接池上限、状态 TTL、内存预算 |
| R-04 | 兼容 | SQLite↔MySQL 切换 | 中 | GORM 抽象、UUID 主键、双驱动 CI 测试、AutoMigrate |
| R-05 | 可用 | etcd 单节点故障（本地） | 中 | 本地缓存兜底、重连退避、生产三节点 |
| R-06 | 可用 | Redis 故障 | 中 | 限流本地降级、熔断本地状态、重连、生产 Sentinel |
| R-07 | 一致 | 热更新多实例不一致 | 中 | 全量拉取+版本校验、60s 兜底同步、atomic.Value |
| R-08 | 安全 | 管理面未授权变更 | 中 | 端口隔离+Token 鉴权+NetworkPolicy+审计+版本回溯 |
| R-09 | 扩展 | 路由规则增多性能下降 | 低 | radix tree O(k)、LRU 缓存、按 Method 分桶 |
| R-10 | 运维 | 灰度比例不精确 | 低 | murmur3 哈希、可选 Redis 计数器、监控告警 |
| R-11 | 可用 | 熔断多实例不一致（P1-1） | 中 | 半开全局计数、状态事件广播、滑动窗口本地判断 |

### 8.2 性能风险应对（R-01/R-02/R-03）

核心措施已在 FL-03 双层限流落实：请求路径操作本地令牌桶，Redis 仅 100ms 批量预取，消除每请求网络往返。辅以异步日志、连接池（MaxIdleConns=1000）、radix tree、sync.Pool、GOGC/GOMEMLIMIT 调优。

验证：wrk -t4 -c100 -d60s，目标 QPS≥10000、延迟<2ms、内存≤80MB。

### 8.3 兼容性风险应对（R-04）

P0-1 已通过 modernc.org/sqlite 解决 cgo 冲突。SQL 兼容性通过 GORM 抽象、UUID 主键、禁止特定函数、AutoMigrate、CI 双驱动测试保障。

### 8.4 可用性风险应对（R-05/R-06/R-11）

- etcd 故障：本地服务实例缓存兜底，重连指数退避，生产三节点
- Redis 故障：限流自动切本地模式，熔断本地独立运行，生产 Sentinel
- 熔断多实例（R-11/P1-1）：半开探测 Redis 全局计数，状态变更发布事件广播，避免阈值与探测数放大

### 8.5 一致性/安全/扩展/运维风险

- 配置一致性（R-07）：全量拉取+版本校验+60s 兜底+atomic.Value，≤60s 收敛
- 安全（R-08）：端口隔离、Token 鉴权、NetworkPolicy、操作审计、配置版本回溯、管理面限流、定期轮换
- 扩展（R-09）：radix tree 支持 10000+ 路由无性能下降，匹配 <0.01ms
- 灰度精度（R-10）：murmur3 分布均匀性≥99%，偏差<2%，监控告警

### 8.6 风险应对总结

| 等级 | 编号 | 策略 | 责任 |
|---|---|---|---|
| 高 | R-01,R-02 | 性能优化：双层限流、异步日志、连接池、对象池 | 后端 |
| 中 | R-03~R-08,R-11 | 降级兜底：本地缓存、内存降级、双驱动测试、熔断全局协调、端口隔离鉴权 | 后端+运维 |
| 低 | R-09,R-10 | 架构设计：radix tree、均匀哈希、监控告警 | 架构师 |

持续监控：每次发布前性能基准测试；CI 双驱动兼容测试；生产大盘实时展示；每月故障演练（etcd/Redis/热更新）。
