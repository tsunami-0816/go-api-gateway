## 三、已修复验证

### 3.1 上一轮引入的回归 Bug

#### REGRESSION-001【P1 严重】一致性哈希 Select() 锁重入死锁，所有 consistent_hash 路由请求超时

| 项目 | 内容 |
|---|---|
| **严重等级** | P1 严重 |
| **验证结果** | ✅ **通过** |
| **验证方式** | 代码审查 + 端到端实测 + 并发稳定性测试 |
| **代码审查** | 1. `UpdateRing()` 加锁后委托调用 `buildRingLocked()`（loadbalance.go 第 120-126 行） 2. 新增 `buildRingLocked()` 纯建环逻辑，不带锁，调用方须已持有写锁（第 128-151 行） 3. `Select()` 的 needRebuild 分支持锁时调用 `buildRingLocked()` 而非 `UpdateRing()`（第 169-178 行），消除锁重入 4. double-check 机制保留，防止竞态条件下重复建环 |
| **端到端实测** | 路由 path=/api/chash, load_balance=consistent_hash, hash_header=X-User-ID；发送 `GET /api/chash -H "X-User-ID: user-001"` → **Status: 200, Time: 42ms** |
| **修复前对比** | 修复前同一场景：HTTP 000, Time: 5015ms（死锁导致超时） |
| **并发稳定性** | 20 并发 × 5 轮 = 100 请求，全部成功（100/100），无死锁、无竞态、无超时 |
| **单元测试** | `TestConsistentHashSelect_NoDeadlock` PASS（首次调用 Select() 2s 内正常返回） |
| **结论** | 锁重入死锁已彻底消除。`Select()` 持锁时调用无锁的 `buildRingLocked()`，不再触发 `sync.RWMutex` 的不可重入阻塞。一致性哈希路由恢复正常，请求快速返回。 |

### 7.4 风险提示

1. **etcd 环境依赖**：本轮测试在 etcd 未运行的降级模式下完成，P0-002 的端到端自注册流程仍未实测（上一轮已通过代码审查确认）。建议 etcd 可用后补充验证。
2. **多实例分布式限流**：P1-007 验证了单实例下 Redis 令牌桶数据正确，多实例部署下的全局配额精确性需在多实例环境中补充验证。
3. **一致性哈希分布均匀性**：当前 `murmur3Hash()` 实际使用 FNV-1a 算法（P3-03），在少量实例下分布可能偏斜。如需更均匀的分布，建议后续替换为真正的 murmur3 实现。
4. **静态后端无健康检查**：静态配置的后端实例不做主动健康探活，实例故障时依赖重试机制容错。生产环境建议使用 etcd 服务注册发现 + lease 机制。
