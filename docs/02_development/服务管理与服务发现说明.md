# 服务管理与服务发现说明

## 架构定位

本网关的"服务管理"与"服务发现"是两个独立的层面，职责分离：

| 层面 | 管理面 Service CRUD | 数据面服务发现 |
|------|---------------------|----------------|
| 存储 | SQLite `gw_service` 表（服务元数据） | etcd `/services/{name}/{id}`（运行时实例） |
| 内容 | 服务名、显示名、健康检查路径、权重等**元数据配置** | 实例 IP:Port、版本、权重、健康状态等**运行时实例** |
| 写入方 | 网关管理面 API | 后端服务自身通过 etcd client 注册 |
| 读取方 | 管理面展示、配置快照 | 数据面反向代理负载均衡 |

## 为什么不联动

管理面 `POST /api/v1/services` 仅注册**服务元数据**，不向 etcd 写入实例 key。原因：

1. **服务实例的生命周期属于服务自身**：实例上线/下线应由服务进程控制（启动时注册、退出时注销），网关不应越俎代庖。
2. **健康检查需要服务配合**：网关无法判断一个手动写入的实例是否真的可用。
3. **多实例场景**：一个服务通常有多个实例，管理面逐个注册不现实。

## 生产环境服务注册方式

后端服务应在启动时通过 etcd client 自行注册：

```go
import "github.com/go-api-gateway/gateway/internal/registry"

inst := &registry.Instance{
    ID:      "instance-uuid",
    Address: "10.0.0.1:8080",
    Weight:  1,
    Version: "v1.0.0",
    Healthy: true,
}
reg, err := registry.NewRegistry(etcdConfig, inst)
defer reg.Deregister()
```

etcd key 格式：`/services/{serviceName}/{instanceID}`，TTL=10s，自动 KeepAlive。

## 本地联调：测试实例注册 API

为方便本地联调（无需启动真实后端服务），管理面提供了测试实例注册端点：

### 注册测试实例

```
POST /api/v1/services/:name/instances
Authorization: Bearer <token>

{
    "address": "127.0.0.1:9090",
    "weight": 1,
    "version": "stable"
}
```

- 向 etcd 写入一个 60s 租约的实例 key（无 KeepAlive，60s 后自动过期）
- 仅用于本地测试，**不可用于生产**

### 注销测试实例

```
DELETE /api/v1/services/:name/instances/:instance_id
```

## 联调验证步骤

1. 启动 etcd
2. 启动网关（管理面 8081、数据面 8080）
3. `POST /api/v1/services` 注册服务元数据
4. `POST /api/v1/services/:name/instances` 注册测试实例（指向一个可用的 HTTP 服务）
5. `POST /api/v1/routes` 创建路由，target_service 指向该服务
6. `GET http://127.0.0.1:8080/{path}` 验证数据面转发成功
