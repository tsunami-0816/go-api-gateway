### 4.2 第二轮新发现问题

#### BUG-11【中等】限流规则 Update 接口乐观锁 version 未传递，连续编辑第二次必返 409

- **现象**：对同一条限流规则连续执行两次 `PUT /api/v1/rate-limits/:id`，第一次成功（200），第二次返回 409 `{"code":40900,"message":"更新失败"}`。
- **根因定位**：`internal/handler/other_handlers.go` 的 `RateLimitHandler.Update` 中构建 `model.RateLimit` 时：
  ```go
  BaseModel: model.BaseModel{ID: c.Param("id"), UpdatedBy: operator},
  // 未设置 Version 字段 → Version=0
  ```
  而 `internal/repository/rate_limit_repository.go` 的 `Update` 使用乐观锁：
  ```go
  Where("id = ? AND version = ?", m.ID, m.Version)  // m.Version=0
  ```
  第一次更新时数据库 version=0，匹配成功，version 递增为 1；第二次更新时请求中 version=0，与数据库 version=1 不匹配，`RowsAffected=0`，返回错误。
- **对比**：`RouteHandler.UpdateRoute` 无此问题，因为它先调用 `h.repo.GetByID()` 读取原有记录，将 `existing.Version` 赋给新构建的 route。
- **影响**：前端用户编辑限流规则时，第一次保存成功，第二次修改保存会失败（409），必须刷新页面重新获取数据后才能再次编辑。用户体验差，且前端无 version 字段传递机制。
- **可复现性**：100% 可复现（实测确认）。
- **复现步骤**：
  1. `POST /api/v1/rate-limits` 创建规则 → 200
  2. `PUT /api/v1/rate-limits/:id` 更新（任意字段）→ 200
  3. 再次 `PUT /api/v1/rate-limits/:id` 更新 → **409 更新失败**

### 4.3 环境限制与遗留说明

## 5. 修复建议

### 5.1 本轮新发现问题修复

#### FIX-11：限流 Update 接口传递乐观锁 version（对应 BUG-11）

**方案 A（推荐，与 RouteHandler 保持一致）**：在 `RateLimitHandler.Update` 中先读取原有记录获取 version，再构建更新 model。

```go
// internal/handler/other_handlers.go RateLimitHandler.Update
func (h *RateLimitHandler) Update(c *gin.Context) {
    var req CreateRateLimitRequest
    if err := c.ShouldBindJSON(&req); err != nil { /* ... */ }

    // FIX-11: read existing record to get current version for optimistic lock
    existing, err := h.repo.GetByID(c.Request.Context(), c.Param("id"))
    if err != nil {
        response.Fail(c, http.StatusNotFound, 40400, "限流规则不存在")
        return
    }

    operator := c.GetString("operator")
    rl := &model.RateLimit{
        BaseModel: model.BaseModel{
            ID:        c.Param("id"),
            Version:   existing.Version,  // FIX-11: pass version
            UpdatedBy: operator,
        },
        // ... 其余字段
    }
    // ...
}
```

**方案 B**：在 `CreateRateLimitRequest` 中增加 `version` 字段，由前端编辑时回传。但此方案需要前端配合修改，且前端当前无 version 管理逻辑，改造成本较高。

**建议采用方案 A**，与 `RouteHandler.UpdateRoute` 的实现模式保持一致，无需前端改动。

**同步检查**：建议同时检查 `CircuitBreakerHandler`（无 Update 接口，无需修改）、`GrayReleaseHandler`（无 Update 接口，仅有 `PatchPercent`，需检查 `UpdatePercent` 是否使用乐观锁）、`ServiceHandler`（无 Update 接口）。经代码审查，`gray_release_repository.go` 的 `UpdatePercent` 未使用乐观锁（直接 `Where("id = ?").Update("gray_percent", ...)`），无此问题。
