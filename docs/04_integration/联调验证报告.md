## 4. 联调问题

### BUG-01【严重】热更新后数据面路由匹配器未同步

- **现象**：管理面创建路由并 `POST /system/reload` 热更新成功（config_version 1→2），配置快照 routes_count=2，但数据面 `GET http://127.0.0.1:8080/api/users` 返回 404 `route not found`。
- **根因定位**：`internal/app/app.go` 中 `SystemHandler.Reload` 仅调用 `snapManager.Reload()` 更新配置快照，未调用 `app.router.Update(snap.Routes)` 更新数据面路由匹配器。网关启动时 `app.router.Update(app.snapManager.Get().Routes)` 仅执行一次。
- **影响**：管理面创建/修改/禁用的路由在数据面完全不生效，网关核心转发能力不可用。
- **可复现性**：100% 可复现。

### BUG-02【严重】数据面限流未接入配置快照

- **现象**：管理面创建限流规则（rate=100, capacity=200, token_bucket），数据面请求不按该规则限流。
- **根因定位**：`internal/app/app.go` 中 `app.rateLimiter = ratelimit.NewRateLimiter(100, 200)` 是全局硬编码限流器，数据面 NoRoute 中 `a.rateLimiter.Allow(route.ID)` 仅按 routeID 创建桶，所有路由共用 rate=100/capacity=200。`configsnap.Snapshot.GetRateLimitsByRouteID()` 方法已存在但未被数据面调用。
- **影响**：管理面配置的不同算法（令牌桶/漏桶）、不同速率、不同维度（route/ip/client_id）的限流规则在数据面完全不生效。
- **可复现性**：代码审查确认，100% 可复现。

### BUG-03【严重】数据面熔断未接入配置快照

- **现象**：管理面创建熔断策略（error_rate_threshold=50, route_id=xxx），数据面不按该策略熔断。
- **根因定位**：`internal/app/app.go` 中 `app.cbManager = circuitbreaker.NewCircuitBreaker("default", ...)` 是单例默认熔断器，数据面 NoRoute 中 `a.cbManager.Allow()` 和 `a.cbManager.Record(...)` 对所有路由/服务共用同一个熔断器。`configsnap.Snapshot.GetCircuitBreakerByRouteID()` 方法已存在但未被数据面调用。
- **影响**：管理面配置的按路由/服务维度、不同阈值的熔断策略在数据面完全不生效。
- **可复现性**：代码审查确认，100% 可复现。

### BUG-04【中等】管理面 CRUD 后未自动触发热更新

- **现象**：路由/限流/熔断/灰度/服务的 Create/Update/Delete 操作仅写数据库，配置快照不更新，必须手动调用 `POST /system/reload` 才能刷新。
- **根因定位**：各 handler 中操作成功后未调用 `snapManager.Reload()`。
- **影响**：与"热更新生效延迟 ≤5s"指标不符，用户操作后需手动触发热更新，体验差且易遗漏。
- **可复现性**：100% 可复现。

### BUG-05【中等】服务管理与服务发现脱节

- **现象**：管理面 `POST /api/v1/services` 注册服务后，etcd 中无对应实例 key，数据面反向代理找不到后端。
- **根因定位**：管理面 Service CRUD 仅写 `gw_service` 表（服务元数据），数据面服务发现依赖 `registry.Discovery` 从 etcd 读取实例。两者无联动机制。
- **影响**：通过管理面"注册服务"无法让数据面实际转发到该服务，服务实例需自行实现 etcd 注册。
- **可复现性**：架构设计层面问题，100% 可复现。

### BUG-06【中等】路由更新后审计字段被零值覆盖

- **现象**：`PUT /api/v1/routes/:id` 更新路由后，返回的 `created_at`、`updated_at` 变为 `0001-01-01T00:00:00Z`，`created_by` 变为空字符串。
- **根因定位**：`internal/handler/route_handler.go` 的 `UpdateRoute` 直接用请求体构建 `model.Route`，未从数据库读取原有记录保留 `created_at`/`created_by` 等不可变字段。GORM Save 时零值覆盖数据库原值。
- **影响**：审计信息丢失，数据一致性被破坏。
- **可复现性**：100% 可复现（实测确认）。

### BUG-07【轻微】限流更新接口字段丢失

- **现象**：`PUT /api/v1/rate-limits/:id` 更新后，`RouteID`、`PathPattern`、`Method`、`HeaderKey` 字段未更新。
- **根因定位**：`internal/handler/other_handlers.go` 的 `RateLimitHandler.Update` 中构建 model 时仅赋值了 `RuleName/Algorithm/Rate/Capacity/LimitBy/Enabled/Description`，遗漏了路由绑定相关字段。
- **影响**：前端编辑限流规则时修改路由绑定不生效。
- **可复现性**：代码审查确认。

### BUG-08【轻微】Prometheus 系统指标恒为 0

- **现象**：`/metrics` 中 `gateway_goroutines`、`gateway_memory_usage_bytes`、`gateway_active_connections` 值恒为 0，而 Go 原生指标 `go_goroutines=12` 正常。
- **根因定位**：`internal/observability/metrics.go` 中定义了这三个 Gauge，但全项目无任何地方调用 `.Set()` 更新其值。
- **影响**：可观测性数据缺失，无法监控网关运行状态。
- **可复现性**：100% 可复现（实测确认）。

### BUG-09【轻微】数据面请求路径无业务指标记录

- **现象**：`gateway_qps_total`、`gateway_request_duration_seconds`、`gateway_error_rate`、`gateway_rate_limit_*`、`gateway_circuit_breaker_*`、`gateway_gray_requests_total` 等业务指标定义存在，但数据面 NoRoute 处理逻辑中无任何 metrics 记录代码。
- **根因定位**：`app.startDataServer()` 的 NoRoute handler 中未注入 `app.metrics` 记录逻辑。
- **影响**：核心业务指标（QPS/延迟/错误率）无法采集，与基线 D-06 要求不符。
- **可复现性**：代码审查确认。

### BUG-10【轻微】数据面限流响应头硬编码

- **现象**：限流拒绝时 `X-RateLimit-Limit` 响应头硬编码为 `"100"`，不随路由配置的 rate 变化。
- **根因定位**：`internal/app/app.go` NoRoute 中 `c.Header("X-RateLimit-Limit", "100")` 硬编码。
- **影响**：客户端无法获取真实限流阈值。
- **可复现性**：代码审查确认。

## 5. 修复建议

### 5.1 严重问题修复（必须优先）

#### FIX-01：热更新同步数据面路由匹配器（对应 BUG-01）

**方案**：在 `configsnap.Manager` 中引入 `OnReload` 回调机制，app 启动时注册各组件的更新回调。

```go
// configsnap/snapshot.go
type ReloadCallback func(snap *Snapshot)

func (m *Manager) OnReload(cb ReloadCallback) {
    m.callbacks = append(m.callbacks, cb)
}

func (m *Manager) Reload(ctx context.Context) (int64, error) {
    // ... 构建新快照 ...
    m.snapshot.Store(snap)
    for _, cb := range m.callbacks {
        cb(snap)
    }
    return m.version, nil
}
```

```go
// app/app.go New() 中注册回调
app.snapManager.OnReload(func(snap *configsnap.Snapshot) {
    app.router.Update(snap.Routes)
    app.rateLimiterManager.Sync(snap.RateLimits)   // 需新增
    app.cbManager.Sync(snap.CircuitBreakers)        // 需新增
})
```

#### FIX-02：数据面限流接入配置快照（对应 BUG-02）

**方案**：新增 `RateLimiterManager`，按规则 ID 管理多个限流器实例，热更新时同步增删改。数据面 NoRoute 中匹配路由后，从快照获取该路由的限流规则列表，逐个检查。

```go
// 数据面 NoRoute 中
snap := a.snapManager.Get()
rules := snap.GetRateLimitsByRouteID(route.ID)
for _, rule := range rules {
    limiter := a.rateLimiterManager.Get(rule.ID)
    if limiter != nil && !limiter.Allow() {
        // 返回 429，X-RateLimit-Limit 使用 rule.Rate
        return
    }
}
```

#### FIX-03：数据面熔断接入配置快照（对应 BUG-03）

**方案**：新增 `CircuitBreakerManager`，按 `route_id` 或 `target_service` 管理多个熔断器实例，热更新时同步。数据面 NoRoute 中获取该路由的熔断策略，使用对应熔断器检查和记录。

```go
// 数据面 NoRoute 中
```
